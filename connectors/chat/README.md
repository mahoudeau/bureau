# chat connector

Turning conversations into Bureau workers. Not a connector in the code sense, and that is the point: the hub itself speaks MCP, so a chat app needs no glue at all. Setup is an address, a sign-in and a paragraph. Licensed Apache-2.0 (`../../LICENSE-APACHE`).

## Setup

The hub walks you through this, one step at a time: `/setup` for consul and sol (Claude, or any other app), `/setup/agent/<name>` for any other agent. By hand:

1. **Turn on sign-in for the agent**, on a hub with sign-in (`../../docs/protocol.md`, "Sign-in"): Settings, Sign-in, add the agent (consul, say) and pick its projects. Its address is `https://<hub>/mcp/agent/consul`. The address holds no secret.
2. **Add it in the chat app**: in claude.ai it is Customize, then Connectors (`https://claude.ai/new#customize/connectors`), then add custom connector; name it after the agent, `Bureau (consul)`, and paste the address. The app finds where to sign in by itself and sends you there: sign in with the hub owner's account and approve.
3. **Allow the app on the Desk.** The hub holds every new app until an owner allows it for that agent ("claude.ai wants to act as consul"). Until then the connector shows its tools, and every one answers that it is waiting. Allow it once; after that it works, and the app refreshes its own sign-in. To cut it off, Deny it or forget it in Settings, Sign-in, or turn the agent's sign-in off.
4. **Tool permissions**: the door has 26 tools. Allow the read tools always (whoami, list_projects, list_missions, list_missions_full, get_mission, read_knowledge, get_context, brain_map, search_knowledge, memory_health, read_work, read_inbox, read_settings, read_journal, recent_activity); put the write tools (create_mission, start_mission, claim_mission, update_mission, apply_item, write_knowledge, capture, write_work, send_message, clock_in, heartbeat) wherever your trust sits: needs-approval gives you a click per action while you watch the flow, always-allow makes it fully fluid.

**A hub without sign-in** uses a URL with a token in it instead: `node hub/tools/token.js mint consul general` (name the agent and its projects; `*` for all) prints it as `MCP URL`. That URL is a capability: whoever has it works your Bureau as that agent, inside its projects, so treat it like a password. Paste it in step 2; skip steps 1 and 3. To rotate it: `node hub/tools/token.js list`, `revoke <id>`, mint again, replace the URL in the app. Once your hub has sign-in, move the connector to the agent's address and close the old URLs with `{"global": {"mcp_token_urls": false}}`.
5. **Make it proactive**: the server teaches connected sessions the shift discipline through its own MCP instructions, which use the agent's name, but instructions answer *how*, not *whether*. To make every conversation reach for the Bureau on its own, add this to the app's global preferences (the envoy's default name is consul; change it here to match your agent):

The setup guide (`/setup`) hands out this text with a copy button. Name the connector after the agent, as the guide does: an instruction that just says "the Bureau connector" is ambiguous once sol's connector sits in the same account.

> When the Bureau (consul) connector is available and the conversation involves substantive work (research, writing, building, planning, analysis), use it on your own initiative, without being asked: I want this work logged in Bureau, and asking me first defeats the point. Use only Bureau (consul), never Bureau (sol), which belongs to sol's nightly routine. Workflow: check list_missions first for queued missions reserved for consul and continue those before anything else; pick the project with list_projects (ask only if genuinely ambiguous, never invent ids); before working, read the scope chain with read_knowledge (global knowledge/ and recipes/, then the project's entity if it has one: entities/<slug>/PROFILE.md and its knowledge/ and recipes/, then projects/<project>/STATE.md; nearest scope wins, and never read another entity's tree); open a mission with create_mission before doing the work; start_mission to claim it; post progress with update_mission at meaningful steps; before finishing, file a debrief with write_knowledge to projects/<project>/STATE.md, three labeled parts: what changed, what was learned, next step; then close the mission done, or review for sign-off. When the boss approves the work in this conversation, close it done directly with his exact words in approved_in_session (if the project's policy doesn't take chat approvals, the hub says so: then park it in review for him), never review for a second approval when the policy takes the quote; review is for work he has not seen, and for irreversible steps (deploys, merges, external sends, purchases, credentials) he has not explicitly approved in the chat. Deliverables worth keeping go to projects/<project>/deliverables/ in the brain, not just the chat. File learnings at the scope where they are true; when unsure, file lower and let the librarian promote. Quick questions and casual conversation need no mission, but after any small task that taught a preference, correction, term, or fact, record it with capture (kind, text: the learning in one line, evidence: how you know); skip it when nothing was learned.

## What a connected conversation can do

Open and work missions, post progress the boss reads on the dashboard, park work for review, read and write the brain, and file journal lines, the same rules as every other worker, enforced by the same hub. Scheduled runs in the same app (where the platform offers them) inherit the connector and the preferences, so recurring chats behave identically.

## Honest limits

Preferences make bureau-first behavior the strong default, not a guarantee: chat models exercise judgment, and an occasional conversation may need a nudge. And a conversation cannot be woken from outside: answered questions and reserved missions are picked up when a session next starts, which is why the scheduled workers exist.
